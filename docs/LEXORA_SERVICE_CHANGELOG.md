# Lexora Service — локальный журнал разработки

> До подключения канонического журнала Google Drive этот файл фиксирует локальные изменения разработки. При подключении канонического журнала записи должны быть сверены по ID.

## SRV-000001 — Foundation Android
- Статус: внесено, сборка не подтверждена
- Тип: архитектура / foundation
- Изменено: Android app shell, multi-module structure, design system, navigation, home/settings, wash/tires placeholders.
- Версия: 0.1.0

## SRV-000002 — Organization context / RBAC / Module registry
- Статус: внесено, сборка не подтверждена
- Тип: архитектура / доступ / модульность
- Модули: core:model, core:domain, core:data, app, feature:home, feature:settings
- Требование: активная организация, базовые роли и права, включение/отключение модулей, проверка лицензии и прав до предоставления доступа.
- Реализовано:
  - ServiceUser, UserRole, Permission;
  - AccessPolicy и ModuleAccessPolicy;
  - OrganizationRepository, UserRepository, ModuleRegistry;
  - локальные in-memory реализации для Foundation;
  - состояния лицензии модулей;
  - ядро нельзя отключить;
  - недоступные/нелицензированные модули не предоставляются главному экрану;
  - экран настроек показывает организацию, пользователя, роли и состояние модулей.
- Ограничение: хранение пока in-memory; Room/offline persistence будет следующим этапом.

## SRV-000003 — Room/offline foundation + core service entities
- Статус: внесено, сборка не подтверждена
- Тип: архитектура / данные / offline-first
- Версия: 0.3.0
- Модули: core:database, core:model, feature:clients, app
- Реализовано:
  - Room database schema v1;
  - сущности Organization, Client, Vehicle, Branch, Employee, ModuleSetting, AuditEvent;
  - DAO для базовых CRUD/read операций;
  - `SyncState` для будущей очереди синхронизации;
  - политика миграций без destructive fallback;
  - базовый экран «Клиенты»;
  - первичное сохранение активной организации и демонстрационного клиента в локальную БД.
- Ограничение: серверная синхронизация, очередь операций и полноценные формы создания/редактирования еще не реализованы.

## SRV-000004 — Полноценный базовый контур «Клиенты»
- Статус: внесено, сборка не подтверждена
- Тип: функциональное / данные / UI/UX / аудит
- Версия: 0.4.0
- Модули: core:model, core:database, feature:clients, app
- Основание: ТЗ v1.2, разделы 5, 7.2, 9, 10, 13, 16, 20, 23, 24.
- Реализовано:
  - список активных клиентов и отдельный просмотр архива;
  - поиск по ФИО/наименованию, телефону, email и ИНН;
  - создание и редактирование физического/юридического лица;
  - телефон, email, ИНН, КПП, регистрационный/юридический и фактический адрес;
  - примечание и признак согласия на обработку персональных данных;
  - базовая проверка ИНН (10/12 цифр) и КПП (9 цифр для юрлица);
  - защита от очевидных дублей по нормализованному телефону и ИНН;
  - архивирование вместо физического удаления и восстановление;
  - audit events CREATE/UPDATE/ARCHIVE/RESTORE;
  - пользовательские строки нового экрана вынесены в resources;
  - изменения клиента получают PENDING_CREATE/PENDING_UPDATE для будущей синхронизации.
- Миграция данных: Room schema 1 -> 2 с сохранением существующих строк clients.
- Проверка сборки: не выполнена — в среде отсутствуют Gradle Wrapper и системный Gradle.
- Следующий этап: автомобили/объекты обслуживания и связи с клиентом.

## SRV-000005 — Core data / Автомобили / сервисная история
- Статус реализации: внесено; сборка не подтверждена.
- Версия: 0.5.0 / versionCode 5.
- Добавлен feature-модуль `feature:vehicles`.
- Реализованы список, поиск, создание, редактирование, архивирование и восстановление автомобилей.
- Поля: владелец, госномер, VIN, марка, модель, год, тип кузова, цвет, пробег.
- Добавлена проверка дубликатов по госномеру и VIN.
- Действия автомобиля фиксируются в общем аудите.
- Room schema v3; миграция 2→3 добавляет тип кузова, цвет и таблицу `service_history`.
- `service_history` является фундаментом общей сервисной истории автомобиля для событий отраслевых модулей.
- Изменения соответствуют ТЗ v1.2, разделам 5, 7.18, 13, 16 и 27.

## SRV-000006 — Core data / Объекты обслуживания и оборудование
- Статус реализации: внесено в `main`; сборка не подтверждена.
- Версия: 0.6.0 / versionCode 6.
- Тип: функциональное / данные / UI/UX / аудит / миграция.
- Модули: `core:model`, `core:database`, `core:navigation`, `feature:home`, `feature:assets`, `app`.
- Реализовано:
  - отдельный feature-модуль `feature:assets`;
  - сущность объекта обслуживания с привязкой к клиенту;
  - поля объекта: название, адрес, режим доступа, ответственное лицо/контакт;
  - сущность оборудования с привязкой к объекту;
  - поля оборудования: тип, производитель/марка, модель, серийный номер, инвентарный номер, QR/штрихкод, заметки о вводе в эксплуатацию и гарантии;
  - список, поиск, создание, редактирование, архивирование и восстановление объектов и оборудования;
  - базовая защита оборудования от дублей по серийному номеру;
  - операции `CREATE`, `UPDATE`, `ARCHIVE`, `RESTORE` фиксируются в общем аудите;
  - новые/измененные записи получают `PENDING_CREATE` / `PENDING_UPDATE` для будущей синхронизации;
  - на главном экране добавлен переход «Объекты и оборудование».
- Миграция данных: Room schema 3→4 через явную `Migration(3, 4)`, добавлены таблицы `service_objects` и `equipment` и индексы; destructive migration не используется.
- Основание: ТЗ v1.2, разделы 2.2, 5, 7.3, 7.4, 13, 16, 20, 23, 24 и 27.
- Проверка сборки: не выполнена — Gradle Wrapper в проекте отсутствует, системный Gradle в текущей среде недоступен.
- Следующий этап: филиалы и сотрудники, затем обращения/заявки и базовый service workflow.

## SRV-000007 — Филиалы и сотрудники
- Статус реализации: внесено в `main`; сборка не подтверждена.
- Версия: 0.7.0 / versionCode 7.
- Тип: функциональное / данные / UI/UX / аудит / миграция.
- Модули: `core:model`, `core:database`, `core:navigation`, `feature:home`, `feature:organization`, `app`.
- Основание: ТЗ v1.2, разделы 3, 4, 5, 7.22, 13, 16, 20, 23, 24 и 27.
- Реализовано:
  - отдельный feature-модуль `feature:organization`;
  - управление активными и неактивными филиалами;
  - филиал: название, адрес, телефон, email, график работы, часовой пояс, статус активности;
  - управление активными и неактивными сотрудниками;
  - сотрудник: ФИО, должность, телефон, email и привязка к филиалу;
  - создание филиалов и сотрудников;
  - деактивация вместо физического удаления и последующее восстановление;
  - все операции `CREATE`, `UPDATE`, `DEACTIVATE`, `ACTIVATE` фиксируются в общем аудите;
  - изменения получают `PENDING_CREATE` / `PENDING_UPDATE` для будущей синхронизации;
  - на главном экране добавлен переход «Филиалы и сотрудники»;
  - данные изолированы по активной организации.
- Миграция данных: Room schema 4→5 через явную `Migration(4, 5)`; добавлены контактные поля филиала, график работы и контакты сотрудника; destructive migration не используется.
- Подготовка к следующему этапу: сотрудники и филиалы могут использоваться при назначении исполнителей и операционного контекста заявок.
- Проверка сборки: не выполнена — Gradle Wrapper в репозитории отсутствует; успешная сборка не заявляется.
- Следующий этап: обращения и заявки, статусы, приоритет, SLA, назначение исполнителя/филиала и базовый service workflow.
