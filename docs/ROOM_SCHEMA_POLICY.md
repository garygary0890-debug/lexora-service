# Lexora Service — политика локальной схемы данных

## Текущая версия схемы
Room database schema version: 4.

## Правила
- Изменение существующей production-схемы выполняется только через явную Migration.
- `fallbackToDestructiveMigration()` в production-конфигурации запрещён.
- Архивирование бизнес-значимых сущностей предпочтительнее физического удаления.
- Каждая изменяемая офлайн-сущность содержит состояние синхронизации.
- Аудит хранится отдельными событиями и не подменяется полем `updatedAt`.
- До подключения сервера `PENDING_*` означает локальное изменение, ожидающее синхронизации.

## Migration 1 -> 2
Добавлены поля клиента:
- `kpp`;
- `registrationAddress`;
- `actualAddress`;
- `note`;
- `consentPersonalData`.

## Migration 2 -> 3
- В `vehicles` добавлены `bodyType` и `color`.
- Добавлена таблица `service_history` с индексами по организации, автомобилю и времени события.

## Migration 3 -> 4
Добавлены таблицы:
- `service_objects` — объекты обслуживания с привязкой к организации и клиенту;
- `equipment` — оборудование с привязкой к организации и объекту обслуживания.

Созданы индексы по `organizationId`, `clientId`, `serviceObjectId` и составной индекс оборудования по организации/серийному номеру.

Все миграции выполняются без удаления существующих пользовательских данных.

## Следующее изменение схемы
При следующем изменении таблиц необходимо:
1. повысить версию базы до 5;
2. добавить явную `Migration(4, 5)`;
3. проверить сохранность клиентов, автомобилей, объектов, оборудования, филиалов и аудита;
4. зафиксировать изменение и результат проверки в SRV-журнале.
