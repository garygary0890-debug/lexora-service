# Lexora Service — политика локальной схемы данных

## Текущая версия схемы
Room database schema version: 9.

## Правила
- Изменение существующей production-схемы выполняется только через явную Migration.
- `fallbackToDestructiveMigration()` в production-конфигурации запрещён.
- Архивирование бизнес-значимых сущностей предпочтительнее физического удаления.
- Каждая изменяемая офлайн-сущность содержит состояние синхронизации.
- Аудит хранится отдельными событиями и не подменяется полем `updatedAt`.
- До подключения сервера `PENDING_*` означает локальное изменение, ожидающее синхронизации.
- Денежные суммы хранятся целыми значениями в минимальных денежных единицах (`Long`).
- Серверная синхронизация должна быть идемпотентной: каждая исходящая операция имеет уникальный `idempotencyKey`.
- Конфликты не должны молча перезаписывать локальные данные; они фиксируются отдельно до явного разрешения.

## Migration 6 -> 7
Добавлены таблицы полевых работ:
- `service_visits`;
- `visit_checklist_items`;
- `visit_work_entries`;
- `visit_material_usage`;
- `visit_photos`.

## Migration 7 -> 8
Добавлены:
- `service_documents` — заказ-наряды, акты и счета, связанные с организацией, заявкой, выездом и клиентом;
- `payments` — плановые и фактические платежи с привязкой к заявке, документу и клиенту.

Для документов создан уникальный индекс `(organizationId, number)`. Для платежей и документов добавлены индексы по основным связям и статусам. Суммы `totalMinor` и `amountMinor` хранятся как целые значения минимальных денежных единиц.

## Migration 8 -> 9
Добавлены таблицы серверной синхронизации:
- `sync_operations` — устойчивый журнал исходящих операций CREATE/UPDATE/DELETE с уникальным `idempotencyKey`, состоянием обработки, числом попыток, временем следующего повтора и последней ошибкой;
- `sync_conflicts` — журнал конфликтов версий с локальным/удалённым снимком и явным вариантом разрешения.

Для очереди созданы индексы по организации, сущности, статусу, времени следующей попытки и уникальный индекс `(organizationId, idempotencyKey)`. Для конфликтов созданы индексы по организации, сущности, решению и времени обнаружения.

Все миграции выполняются без удаления существующих пользовательских данных.

## Следующее изменение схемы
При следующем изменении таблиц необходимо:
1. повысить версию базы до 10;
2. добавить явную `Migration(9, 10)`;
3. проверить сохранность core-данных, заявок, выездов, документов, платежей, очереди синхронизации, конфликтов и аудита;
4. зафиксировать изменение и результат проверки в каноническом SRV-журнале.
