# Lexora Service — политика локальной схемы данных

## Текущая версия схемы
Room database schema version: 20.

## Правила
- Изменение существующей production-схемы выполняется только через явную Migration.
- `fallbackToDestructiveMigration()` в production-конфигурации запрещён.
- Архивирование бизнес-значимых сущностей предпочтительнее физического удаления.
- Каждая изменяемая офлайн-сущность содержит состояние синхронизации.
- Аудит хранится отдельными событиями и не подменяется полем `updatedAt`.
- До подключения сервера `PENDING_*` означает локальное изменение, ожидающее синхронизации.
- Денежные суммы хранятся целыми значениями в минимальных денежных единицах (`Long`).
- Серверная синхронизация должна быть идемпотентной: каждая исходящая операция имеет уникальный `idempotencyKey`.
- Конфликты не должны молча перезаписывать локальные данные; они фиксируются отдельно до явного разрешения.
- Открытые токены клиентского кабинета в локальной БД не хранятся: сохраняется только SHA-256 hash, срок действия и состояние доступа.
- Пароли, access/refresh tokens и иные секреты пользователя в таблицах профиля и RBAC не хранятся.

## Миграции
- 1→2: расширение карточки клиента.
- 2→3: расширение автомобиля и `service_history`.
- 3→4: `service_objects`, `equipment`.
- 4→5: контакты/график филиалов и сотрудников.
- 5→6: `service_requests`, `request_status_history`.
- 6→7: выезды, чек-листы, работы, материалы и фото.
- 7→8: `service_documents`, `payments`.
- 8→9: `sync_operations`, `sync_conflicts`.
- 9→10: `wash_posts`, `wash_queue`, `wash_tech_cards`, `wash_chemical_usage`.
- 10→11: `tire_queue`, `tire_diagnostics`, `tire_work_entries`, `tire_storage`.
- 11→12: `service_catalog`, `price_lists`, `price_list_items`.
- 12→13: `work_order_items` для состава заказ-наряда и согласования дополнительных работ.
- 13→14: `loyalty_accounts`, `loyalty_transactions`, `quality_control` для программы лояльности и контроля качества.
- 14→15: `service_contracts` для договоров с клиентами, сроков действия, статусов, филиала, файла и архивирования.
- 15→16: `public_bookings`, `portal_access_grants` для фундамента онлайн-записи и клиентского кабинета без установки приложения.
- 16→17: `reference_directories`, `reference_directory_items` для настраиваемых справочников организации.
- 17→18: `service_recipes`, `service_recipe_components` для конструктора состава услуг.
- 18→19: `service_notifications` для единого центра уведомлений организации.
- 19→20: `service_users`, `user_organization_roles` для постоянного хранения пользователей и ролей по организациям.

## Заказ-наряды
`work_order_items` хранит снимок наименования, количества, единицы и цены услуги на момент включения в заказ-наряд. Это позволяет сохранить историческую стоимость даже после изменения прайс-листа.

Дополнительные работы имеют статус согласования `PENDING / APPROVED / REJECTED`; обычные позиции используют `NOT_REQUIRED`. В итог `service_documents.totalMinor` включаются базовые позиции и только согласованные дополнительные работы.

## Лояльность и контроль качества
`loyalty_accounts` содержит текущий бонусный баланс с уникальностью пары `(organizationId, clientId)`. Каждое изменение баланса фиксируется отдельной записью `loyalty_transactions`.

Списание выполняется атомарным условным обновлением и не допускает отрицательный бонусный баланс. Операция списания не записывается, если доступного баланса недостаточно.

`quality_control` связывает контроль качества с существующей заявкой, клиентом и автомобилем. Проверка создаётся только после завершения работ. Статусы: `PENDING / PASSED / ISSUE_FOUND / RESOLVED`.

## Договоры
`service_contracts` хранит договор клиента с организацией без дублирования клиента или филиала. Номер уникален внутри организации. Договор содержит предмет, статус, период действия, дату подписания, ссылку на внешний файл, примечание, архивный признак и `SyncState`.

Допустимый workflow: `DRAFT → ACTIVE / TERMINATED`, `ACTIVE → SUSPENDED / TERMINATED / EXPIRED`, `SUSPENDED → ACTIVE / TERMINATED / EXPIRED`. Терминальные статусы `TERMINATED` и `EXPIRED` не переводятся дальше автоматически.

## Клиентский кабинет и онлайн-запись
`public_bookings` является входным контуром публичной записи и не заменяет `service_requests`. Запись может быть подтверждена, отменена или отклонена. Только подтверждённая запись может быть преобразована в обычную `ServiceRequest`; после конвертации сохраняется `convertedRequestId`, а повторная штатная конвертация запрещается.

При конвертации используются существующие `clientId`, `vehicleId`, `branchId` и желаемая дата записи. Номер заявки формируется в общей последовательности `REQ-*` по всем сохранённым заявкам организации.

`portal_access_grants` хранит только SHA-256 hash токена, клиента, статус, срок действия и время отзыва. Открытый токен возвращается только в момент выдачи и не сохраняется в Room.

Полноценный публичный Web UI и внешний HTTP API этим этапом не реализуются — таблицы и repository являются фундаментом для будущего клиентского кабинета и онлайн-записи без установки Android-приложения.

## Настраиваемые справочники
`reference_directories` хранит справочники конкретной организации. Код справочника уникален внутри организации. Системный признак резервирует возможность защищённых справочников, которые нельзя штатно деактивировать.

`reference_directory_items` хранит значения справочника. Код значения уникален внутри одного справочника; `sortOrder` задаёт стабильный пользовательский порядок. Справочник и его значения имеют признак активности и `SyncState`.

Справочники не заменяют системные enum/workflow-статусы заявок, документов, платежей и других сущностей, пока конкретное поле явно не переведено на reference-data контракт. Это предотвращает нарушение существующих переходов состояний.

## Конструктор услуг
`service_recipes` хранит один шаблон состава для существующей позиции `service_catalog`. Пара `(organizationId, serviceCatalogItemId)` уникальна, поэтому конструктор не создаёт второй каталог услуг.

`service_recipe_components` хранит упорядоченные компоненты типов `WORK` и `MATERIAL`. Для компонента сохраняются наименование, количество, единица, расчётная стоимость единицы, порядок, активность и `SyncState`. Расчётная стоимость шаблона получается суммой активных компонентов и не заменяет клиентскую цену из `price_list_items`.

## Уведомления
`service_notifications` хранит уведомления конкретной организации с типом, приоритетом, заголовком, сообщением, опциональной связью с исходной бизнес-сущностью, временем планового события, временем создания, признаком прочитанности, архивом и `SyncState`.

Генератор уведомлений использует детерминированные ID для заявок, SLA и согласований дополнительных работ. Повторный refresh не создаёт дубликаты и не сбрасывает уже установленную прочитанность существующего уведомления.

На текущем этапе локальный центр уведомлений не заменяет системные Android push-уведомления и не подключает FCM. Внешняя доставка будет отдельным интеграционным этапом после серверного контура.

## Пользователи и RBAC
`service_users` хранит локальный профиль пользователя без пароля и токенов. `user_organization_roles` хранит членство и роли пользователя отдельно для каждой организации; первичный ключ `(userId, organizationId, role)` позволяет одному пользователю иметь несколько ролей в одной организации и разные наборы ролей в разных организациях.

Текущий offline bootstrap создаёт локального администратора только при отсутствии сохранённого профиля и роли `ADMIN`. После создания пользователь читается через `PersistentUserRepository`, а не из `InMemoryUserRepository`. Назначение и отзыв ролей, а также активация/деактивация пользователя должны сопровождаться событиями `audit_events`.

Все миграции выполняются без удаления существующих пользовательских данных.

## Следующее изменение схемы
При следующем изменении таблиц необходимо:
1. повысить версию базы до 21;
2. добавить явную `Migration(20, 21)`;
3. проверить сохранность core-данных, пользователей/RBAC, заявок, выездов, документов, платежей, каталогов, прайс-листов, конструктора услуг, уведомлений, заказ-нарядов, лояльности, контроля качества, договоров, публичных записей, portal access, справочников, отраслевых модулей, очереди синхронизации, конфликтов и аудита;
4. зафиксировать изменение и результат проверки в каноническом SRV-журнале.
