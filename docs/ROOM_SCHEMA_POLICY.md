# Lexora Service — политика локальной схемы данных

## Текущая версия схемы
Room database schema version: 7.

## Правила
- Изменение существующей production-схемы выполняется только через явную Migration.
- `fallbackToDestructiveMigration()` в production-конфигурации запрещён.
- Архивирование бизнес-значимых сущностей предпочтительнее физического удаления.
- Каждая изменяемая офлайн-сущность содержит состояние синхронизации.
- Аудит хранится отдельными событиями и не подменяется полем `updatedAt`.
- До подключения сервера `PENDING_*` означает локальное изменение, ожидающее синхронизации.

## Migration 1 -> 2
Добавлены поля клиента: `kpp`, `registrationAddress`, `actualAddress`, `note`, `consentPersonalData`.

## Migration 2 -> 3
- В `vehicles` добавлены `bodyType` и `color`.
- Добавлена таблица `service_history` с индексами по организации, автомобилю и времени события.

## Migration 3 -> 4
- Добавлены `service_objects` и `equipment`.
- Созданы индексы по организации, клиенту, объекту обслуживания и серийному номеру оборудования.

## Migration 4 -> 5
- В `branches` добавлены `phone`, `email`, `workSchedule`.
- В `employees` добавлены `phone`, `email`.

## Migration 5 -> 6
- Добавлены `service_requests` и `request_status_history`.
- Создан уникальный индекс `(organizationId, number)` для номера заявки и индексы поиска/истории.

## Migration 6 -> 7
Добавлены таблицы полевых работ:
- `service_visits` — плановые и фактические выезды по заявкам;
- `visit_checklist_items` — чек-листы выезда;
- `visit_work_entries` — выполненные работы;
- `visit_material_usage` — использованные материалы;
- `visit_photos` — локальные ссылки и метаданные фотографий.

В `service_visits` предусмотрены плановые/фактические интервалы, исполнитель, филиал, результат работ, имя клиента и ссылка на подпись. Все изменяемые записи содержат `syncState` для offline-first синхронизации.

Все миграции выполняются без удаления существующих пользовательских данных.

## Следующее изменение схемы
При следующем изменении таблиц необходимо:
1. повысить версию базы до 8;
2. добавить явную `Migration(7, 8)`;
3. проверить сохранность core-данных, заявок, истории статусов, выездов, чек-листов, работ, материалов, фото и аудита;
4. зафиксировать изменение и результат проверки в каноническом SRV-журнале.
