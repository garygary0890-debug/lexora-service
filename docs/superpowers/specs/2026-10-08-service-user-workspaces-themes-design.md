# Lexora Service: пользовательские рабочие пространства, темы и экраны

**Дата:** 8 октября 2026 г.  
**Статус:** концепция одобрена в чате; письменная спецификация ожидает проверки владельцем проекта.  
**Основа:** `feature/srv-103-navigation-menu-search`, commit `7fcee1314fb98d7a057e8b17d10d288fb471fdfb`.

## 1. Цель и границы

Внести в Lexora Service пакет изменений: перейти от организации как владельца и контекста доступа к пользователю-владельцу, сохранить командный доступ между пользователями, добавить 22 темы Lexora Debt и обновить экраны оперативной сводки, меню и планирования.

Изменения выполняются только в репозитории `garygary0890-debug/lexora-service`. Отдельные проекты и серверный репозиторий не изменяются. Контракт сервера проверяется со стороны клиента; если он требует изменения вне Lexora Service, несовместимость фиксируется как блокер, а не маскируется локальным поведением.

Эта спецификация уточняет и заменяет положения ТЗ v1.2 об организации как обязательном владельце данных, об активной организации и об изоляции по организации. Ранее пользователь подтвердил полное удаление организаций как сущности и перенос командного доступа на пользователей.

## 2. Модель пользователя и команды

1. `ServiceUser` становится единственным субъектом владения рабочими данными и основой контекста доступа.
2. В бизнес-данных поле `organizationId` заменяется на `ownerUserId`. Записи рабочей области видны её владельцу и пользователям, которым владелец предоставил доступ через пользовательские связи и роли.
3. Организационная сущность, активная организация, создание/переключение организаций, организационные экраны, репозитории и тексты интерфейса удаляются. Командное членство и роли выражаются связями пользователей; отдельная сущность-замена организации не вводится.
4. Филиалы, сотрудники и настройки модулей сохраняются как бизнес-данные/настройки пользовательской рабочей области, если это не требует отдельной группирующей сущности.
5. Доступ по умолчанию не становится глобальным: пользователь видит только собственную рабочую область и рабочие области, доступ к которым ему явно выдан.
6. Исторические записи, аудит, идентификаторы и связи сохраняются. Версионная миграция Room переносит организационные ключи на пользователей и преобразует членство в связи пользователей. До удаления старых таблиц миграция проверяет, что для каждой прежней области однозначно определён пользователь-владелец и сохранены участники/роли. При неоднозначном сопоставлении миграция не удаляет и не объединяет данные молча: требуется разрешение конфликта.
7. Если после преобразования внутри одной пользовательской рабочей области конфликтуют уникальные номера заявок, конфликт разрешается транзакционно с обновлением зависимых ссылок и аудитом; остальные идентификаторы и связи остаются прежними.
8. Проверяются DAO-запросы, репозитории, RBAC, модульные лицензии/настройки, аудит, офлайн-очередь и синхронизация. В исходниках и интерфейсе не остаётся активных организационных контрактов; упоминание старой таблицы допустимо только в миграции истории данных и документации перехода.

## 3. Темы оформления

Экран настроек темы размещается отдельным пунктом в настройках профиля под управлением пользователей и команды. Он содержит 11 цветовых семейств Lexora Debt, каждое в светлом и тёмном режиме:

| Семейство | Светлая | Тёмная |
|---|---:|---:|
| Жемчуг | ✓ | ✓ |
| Графит | ✓ | ✓ |
| Бургунди | ✓ | ✓ |
| Изумруд | ✓ | ✓ |
| Сапфир | ✓ | ✓ |
| Аметист | ✓ | ✓ |
| Петроль | ✓ | ✓ |
| Сталь | ✓ | ✓ |
| Золото | ✓ | ✓ |
| Серебро | ✓ | ✓ |
| Бронза | ✓ | ✓ |

Итого: 22 сочетания «цветовое семейство + режим». Переключатель «Светлая / Тёмная» меняет режим для выбранного семейства. Цвета задаются семантическими токенами, а не локальными цветами отдельных экранов. Все новые и затронутые экраны проверяются в светлом и тёмном режимах. Сохранение и мгновенное применение выбора следует существующему пользовательскому сценарию Lexora Debt; изменение не должно менять геометрию компонентов.

## 4. Оперативная сводка

Шесть показателей в сетке (открытые заявки, срочные, просроченные, выезды сегодня, активные сотрудники, не синхронизировано) получают одинаковую высоту и одинаковые правила выравнивания. «Ожидаемые платежи» остаются отдельной широкой панелью и не обязаны совпадать по размеру с KPI-панелями. Переносы подписей и пустые/большие значения не меняют размер соседних панелей.

## 5. Экран «Меню»

Действие «Настроить нижнее меню» доступно из overflow-меню (меню дополнительных действий по значку с тремя точками) в топбаре экрана «Меню». Отдельная кнопка настройки нижней навигации на самом экране убирается. Сохранение состава и порядка нижней навигации остаётся прежним, если текущее состояние репозитория уже поддерживает эту настройку.

## 6. Экран «Планирование»

Заголовок «Планирование» показывается только в топбаре. Дублирующий заголовок в содержимом экрана удаляется. Навигация по датам располагается одним рядом: шеврон назад, широкая кнопка «Сегодня» на всё свободное пространство, шеврон вперёд. Шевроны заменяют текущие круглые кнопки «Назад» и «Вперёд» и сохраняют их действия. Режимы день/неделя/месяц и отображение выбранной даты сохраняются.

## 7. Проверяемые критерии приёмки

- В приложении и активной модели/контракте нет организации как сущности; миграция данных не теряет записи, связи, аудит, синхронизационный статус и командные права.
- Пользователь без членства не получает доступ к чужой рабочей области; пользователь с членством получает доступ, предусмотренный назначенной ролью.
- На экране темы доступны ровно 22 сочетания: 11 семейств × 2 режима; выбор сохраняется после перезапуска и применяется к приложению.
- Шесть KPI-панелей оперативной сводки равны по размеру; «Ожидаемые платежи» остаются отдельной широкой панелью.
- Настройка нижнего меню открывается из overflow-меню экрана «Меню» и продолжает сохранять выбранный состав/порядок.
- На планировании заголовок остаётся в топбаре; кнопка «Сегодня» занимает свободную ширину между работающими шевронами.
- Сборка `:app:assembleDebug`, существующие тесты и новые миграционные/тематические/навигационные проверки завершаются успешно.
- Журнал разработки и диагностический статус сборки обновлены фактическими результатами; статус «проверено» ставится только после прохождения критериев.

## 8. Ограничения и риски

Удаление организации меняет фундаментальный контракт ТЗ v1.2. До реализации требуется проверить фактические данные и контракт API. Нельзя удалять старые таблицы до успешного переноса и проверки целостности. Поскольку работа ограничена репозиторием Lexora Service, изменения серверной части или других продуктов Lexora в объём не входят.
